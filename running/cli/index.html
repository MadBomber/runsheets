    Command line Configuration Running

    Command Line¶

    Usage: runsheets [options] [RUNBOOK]
       runsheets --new [DIR]
       runsheets --run [STEP] --engineer NAME --why TEXT [RUNBOOK]

    RUNBOOK is one of three things: a runbook directory (it must contain runbook.md), a single all-in-one markdown file whose ## headings are the steps (see Single-file runbooks), or a directory holding several of either, in folders nested to any depth (see Choosing a runbook). Given such a directory of runbooks, the page opens on a folder tree and the operator picks one; runsheets examples shows the five bundled example runbooks that way. It is the only positional argument. Leave it out and the bundled examples/directory_based_runbooks/hello is served, which is the quickest way to see the tool. dir: in the config file or RUNSHEETS_DIR can supply it instead; see Settings. A relative RUNBOOK is looked for in the current directory first, then under the dir: a config file sets, else RUNSHEETS_DIR (a dir: naming a single-file runbook is searched from the folder it is in). With RUNSHEETS_DIR=~/ops/runbooks, runsheets --check platform/deploy finds ~/ops/runbooks/platform/deploy from anywhere. An absolute path, or one starting with ~, is only ever looked for where it says. When neither place has it, the error names both. --new [DIR] takes no RUNBOOK and cannot be combined with --run; see New runbooks. --run [STEP] runs one step of RUNBOOK at the terminal; see Running one step.

    Options¶

    Option Default Meaning
    -c, --config FILE ./config/runsheets.yml Config file to read in place of the project config; see Settings. A file named here must exist.
    -p, --port PORT 4567 Port to listen on, from 1 to 65535.
    -b, --bind HOST 127.0.0.1 Address to bind to. See the note below before changing it.
    --runs-dir DIR ~/.local/share/runsheets/runs Where session records, logs and run records are written.
    -o, --open off Open the default browser once the server is listening. --no-open turns it off.
    --check off Load the runbook, print authoring warnings, and exit without serving. On a directory of runbooks, every runbook is checked, one line each. See Checking runbooks. --no-check turns it off.
    --new [DIR] Ask what kind of runbook to make, write it into DIR from a template, and exit. Without DIR, ask for it too. See New runbooks.
    --run [STEP] Run one step of RUNBOOK at the terminal and exit. STEP is the step's name or slug, or verify, rollback or runbook, never a number; without it, the steps are listed to choose from by number. Needs --engineer and --why. See Running one step.
    --dump off Print the settings in force as a config file to stdout and exit. --no-dump turns it off. See Saving settings.
    -e, --engineer NAME ask Who is starting the session. Without it the start page asks, pre-filled from git config user.name, else $USER. See The session.
    -w, --why TEXT ask Why the session is being started: its first note. With --engineer too, the session starts at once and the start page is skipped.
    --log-level LEVEL info The session log's level: debug, info, warn, error or fatal, in any case. See The session log.
    --verbose The same as --log-level debug.
    -q, --quiet off Do not echo the session log to the terminal. --no-quiet turns it off.
    -v, --version Print the version and exit.
    -h, --help Print usage and exit.

    Examples¶

    Start a new runbook, then serve it:

    runsheets --new ops/runbooks                    # answer the questions; say db-refresh for the name
runsheets --open ops/runbooks/db-refresh

    Serve a runbook and open it, as a directory or as one all-in-one file:

    runsheets --open ops/runbooks/staging-teardown       # a directory
runsheets --open ops/runbooks/db-maintenance.md      # a single file
runsheets --open ops/runbooks                        # choose among them

    Serve on another port because something else has 4567:

    runsheets -p 4580 ops/runbooks/staging-teardown

    Start the session from the command line, skipping the start page:

    runsheets -e "Pat Doe" -w "rotate the staging database password" ops/runbooks

    Keep run records inside a project (but outside the runbook):

    runsheets --runs-dir ./tmp/runs ops/runbooks/staging-teardown

    Run the checks in a runbook's verify.md from cron, failing if any does:

    runsheets --run verify -e cron -w "nightly health check" ops/runbooks/db-maintenance.md </dev/null

    Validate every runbook in a repository (a directory of runbooks is checked as a whole):

    runsheets --check ops/runbooks

    New runbooks¶

    runsheets --new DIR asks six questions, shows what it will create and asks to go ahead, then writes a starter runbook into DIR, creating DIR if it does not exist. Enter accepts the default in brackets.

    Leave DIR out and there is a seventh question first: where to put it. The default offered is the dir: a config file sets (the file --config names or ./config/runsheets.yml, then the user config), else RUNSHEETS_DIR. Here a config file setting beats the environment, the reverse of the usual layering, because the config file is where a standing choice of runbook directory belongs. With neither there is no default and an answer is needed. A dir: naming a single-file runbook offers the directory it is in, and ~ is expanded. An answer that names a file, or a ~user that does not exist, is asked for again.

    $ RUNSHEETS_DIR=~/ops/runbooks runsheets --new
Directory to create the runbook in [/Users/you/ops/runbooks]:
New runbook in /Users/you/ops/runbooks
...

    With DIR given:

    $ runsheets --new ops/runbooks
New runbook in ops/runbooks

Shape:
  1) directory    runbook.md, steps/, verify.md and rollback.md
  2) single-file  one .md file; each ## heading is a step
Choose [1]:
Template:
  1) checks    Checks only: verify steps that read and compare, never change
  2) tasks     Checks and tasks: preflight, automated and manual steps, verify
  3) rollback  Checks, tasks and rollback: a destructive step and the way back
  4) timeouts  Checks, tasks and time: per-step timeouts, a background process, a terminal step
  5) inputs    Checks, tasks and inputs: defaults, a secret, another language
  6) asgard    Checks and tasks as asgard tasks in .loki files beside the runbook
Choose [2]: 3
Name (the directory name) [new-runbook]: DB Refresh
Title [Db refresh]: Refresh staging from production
When to use, in a sentence [edit later]: Before a release that needs production data
Who to call when a step fails [edit later]: #data-platform

Create directory runbook ops/runbooks/db-refresh from the rollback template? [Y/n]:
created ops/runbooks/db-refresh/runbook.md
...
    • Shape is the runbook structure: a directory, or one markdown file whose ## headings are the steps.
    • Template is the starting content, from the simplest structure to richer ones; tasks is the default. Every template produces either shape, and every one passes --check with no warnings as written.
    • Name becomes the directory or file name: lower case, with anything but letters and digits turned into -, and .md added for a single file. A name that is already taken (a file, or a directory with anything in it) is asked for again.
    • Title, When to use and Who to call go into the front matter as title, when_to_use and escalation. Left blank, the last two keep a placeholder to fill in later.

    Answering n at the end creates nothing, as does Ctrl-C at any question. The answers can be piped in, one per line. Any missing at the end take their defaults, and the final question is answered yes, so a pipe that runs out writes the runbook:

    printf '2\ninputs\nnightly-report\n' | runsheets --new ops/runbooks

    An answer that is refused (a name that is taken, a choice not on the list) with no more input after it is an error, not a default.

    The bundled templates¶

    The templates are a ladder of structure, not of subject: each adds one thing to the one before, so pick the simplest that has what your procedure needs and replace the placeholder commands.

    # Template Adds What is in it
    1 checks checks only Steps that are all kind: verify: commands that read, never change, each compared with a text expect block. Runnable all at once from the Checks page.
    2 tasks doing work A preflight check, an automated step, a manual step, and verify.md, with one input, WORK_DIR. The default.
    3 rollback undoing work tasks, plus a step that keeps a copy, a destructive step behind a typed confirmation, and rollback.md to put the copy back.
    4 timeouts time tasks, plus a timeout per step, a background block that runs while later steps do, and a terminal block for the operator's own shell.
    5 inputs inputs tasks, driven by inputs: one with a default, one without, a secret that is redacted from the output, and a python block run through interpreters.
    6 asgard code beside the runbook tasks, with every block a one-line asgard call and the code in .loki files beside the runbook.

    Rungs 4 to 6 each build on tasks, not on each other, so each shows only its own addition.

    The templates live in templates/ in the gem, one directory each, written as a directory runbook (runbook.md.erb, steps/*.md.erb, verify.md.erb, rollback.md.erb) with a template.yml holding the menu order and description. Files ending in .erb have the answers filled in; any other file is copied as it is. The single-file shape is made from the same files: each step becomes a ## section, and its front matter, less the title, becomes the attribute comment under the heading.

    A template that brings files besides the runbook, as asgard brings its .loki files, cannot drop them loose beside a single file: they would land in a folder other runbooks share, and asgard would use them for every one of those. So a single file from such a template gets a folder of its own, NAME/NAME.md with the support files beside it, and --check is given NAME/NAME.md.

    Running one step¶

    runsheets --run STEP RUNBOOK runs one step at the terminal and exits, without starting the web server. Name the step by its name (take-a-backup), its whole slug (020-take-a-backup), or verify, rollback or runbook for those documents. In a single-file runbook the name is the heading as a slug: ## Take a backup is take-a-backup. STEP is never a number: --run 020 is an error, so a number typed by habit cannot run a step other than the one meant. A name that matches nothing, or more than one step, is an error that names the runbook and lists its steps.

    runsheets --run take-a-backup -e "Pat Doe" -w "refresh staging" ops/runbooks/db-refresh

    A whole slug always means its own document. A numbered step named like verify.md, rollback.md or the landing page (030-verify, say) is reached by its whole slug, since --run verify runs verify.md; --check warns about such a step.

    Leave STEP out and the steps are listed to choose from. Numbers belong here: they are places in this list, not step numbers. A name or slug works too:

    $ runsheets -e "Pat Doe" -w "refresh staging" --run ops/runbooks/db-refresh
Steps in Refresh the staging database:
   1) 010-preflight      Preflight
   2) 020-take-a-backup  Take a backup
   3) 030-tail-the-log   Tail the log  (page only)
   4) verify             Verify
Which step? (its number in the list, or its name): 2

    The list starts with runbook, the landing page, when that page has blocks to run or confirm. A step marked (page only) has a background block and cannot run at a terminal.

    Since the step is optional, --run ops/runbooks/db-refresh would read the runbook as the step. When no other RUNBOOK is given, a value with a /, ending in .md, or naming something in the current directory is taken as RUNBOOK instead. With no RUNBOOK at all, --run uses the dir: or RUNSHEETS_DIR setting, else the bundled hello example. RUNBOOK must be one runbook: --run refuses a directory of them.

    It is recorded like a run from the page. --engineer and --why are required (or engineer: and why: from another settings layer), since there is no start page to ask. The step runs in a session of its own that ends when the step does, with a run record and a session log whose last line says whether the step succeeded, failed or was interrupted. A step that would be refused, or a name that finds no step, starts no session. Unless --quiet is given, the log is echoed as it is written, so each block's output appears as it comes.

    Each block does at the terminal what it does on the page:

    Block At the terminal
    run Runs. A block that does not exit 0 fails the step, and the blocks after it are not run.
    text expect Is compared with the output of the block above it. A mismatch prints the lines that differ, marked - (expected) and + (output), and fails the step.
    destructive Prints its confirmation code and runs only once the code is typed. There is no way to skip this.
    terminal Is printed, and asks Did you run it?, then for an optional note.
    background Is refused. A step with one is not run at all: nothing would be left to stop it. Start it from the page.

    A step with nothing to run or confirm is printed, and asks Done?. A numbered step that succeeds is marked done in the run record.

    First it asks for each of the runbook's inputs in order, as the page's start form does. The value in brackets is the one it has now, from the environment or its default, and Enter keeps it. A secret is read without echo and shown only as [set]; only its newline is removed, so spaces typed around a password are kept, as on the page. An input the step uses that is still blank is an error.

    Who should be greeted? (NAME) [world]: Pat
A word that must never appear in the run record (SECRET_WORD) [set]:
Say hello [010-say-hello]

    Questions are read from standard input. When it runs out (a cron job, or a redirect from /dev/null), the inputs keep their values unasked, and a question that needs a person fails the step instead of waiting. So --run verify can run unattended as a health check, as long as its blocks only run and compare.

    Checking runbooks¶

    --check loads the runbook, prints its authoring warnings to stderr prefixed runsheets: warning:, and prints one line to stdout:

    Hello, runsheets: 6 steps, 0 warnings

    On a directory of runbooks every runbook gets that line with its slug in brackets, and each warning is prefixed with the slug:

    runsheets: warning: platform/deploy: 020-roll-out: automated step has no executable block
Deploy [platform/deploy]: 4 steps, 1 warnings
Backup [platform/database/backup]: 3 steps, 0 warnings

    A runbook in the directory that cannot be read (an unreadable file, front matter that is not valid YAML, a clash of names) is never dropped from the check. It is reported as an error with its slug and no summary line:

    runsheets: error: platform/restore: front matter may not use YAML aliases (& and *)

    The exit status is 1 if any runbook warned or could not be read, else 0.

    What it prints¶

    runsheets 0.0.1
Runbook: Staging Infrastructure Teardown and Rebuild (/Users/you/ops/runbooks/staging-teardown)
Runs:    /Users/you/.local/share/runsheets/runs
Config:  /Users/you/.config/runsheets/runsheets.yml
Session: starts in the browser (who and why)
Open http://127.0.0.1:4567/?token=3f9c0d6e8a1b4c2f9e7d5a3b1c0f8e6d in your browser
Press Ctrl-C to end the session and stop

    The link carries this start's session key. Opening it gives the browser the key as a cookie and drops it from the address bar; every request needs the key, so another account on the machine that can reach the port still sees nothing. --open opens this link. Each start makes a new key, so a tab or bookmark from an earlier start shows "Open the link from the terminal" until the new link is opened. With an IPv6 --bind the address is bracketed, http://[::1]:4567/?token=….

    Started on a directory of runbooks, the second line is Library: with the number of runbooks and folders. When --engineer and --why are both set the session has already started, and the Session: line gives its id and the path of its log:

    Session: 20261010T141502, log /Users/you/.local/share/runsheets/runs/sessions/20261010T141502/session.log

    Served on one runbook, its authoring warnings are printed to stderr before the banner, prefixed runsheets: warning:. The server still starts; warnings mark blocks and steps in the page but do not block serving. In a library, each runbook's warnings are on its pages and in --check.

    Puma then prints its own startup lines. From then on, unless --quiet is given, the session log is echoed to the terminal as it is written. Press Ctrl+C to end the session and stop; see Stopping.

    Exit status¶

    Status When
    0 Normal exit, --check found no warnings, --new wrote a runbook, or the --run step succeeded.
    1 Bad arguments or settings, the runbook could not be loaded, the port is in use, --check found warnings or a runbook it could not read, --new was answered n or could not write, or the --run step failed, was refused, or was not confirmed.
    130 Ctrl-C at a --new question, or during --run.

    Settings¶

    Every option is a setting with the same name (port, bind, runs_dir, open, check, dump, engineer, why, log_level, quiet), and the RUNBOOK argument is the setting dir. --verbose sets log_level to debug. Settings are layered with myway_config; each layer overrides the one below it, and anything a layer leaves out comes from further down:

    1. Command line. Whatever is given wins outright.
    2. Environment variables, RUNSHEETS_ plus the setting name in upper case: RUNSHEETS_PORT, RUNSHEETS_BIND, RUNSHEETS_RUNS_DIR, RUNSHEETS_OPEN, RUNSHEETS_CHECK, RUNSHEETS_DUMP, RUNSHEETS_DIR, RUNSHEETS_ENGINEER, RUNSHEETS_WHY, RUNSHEETS_LOG_LEVEL, RUNSHEETS_QUIET.
    3. The project config, ./config/runsheets.yml in the current directory, or the file --config FILE or RUNSHEETS_CONFIG names in its place. The project file may be absent; a file named explicitly must exist.
    4. The user config, ~/.config/runsheets/runsheets.yml (or under $XDG_CONFIG_HOME), which myway_config reads for every application. This is where personal settings belong.
    5. Bundled defaults, lib/runsheets/config/defaults.yml inside the gem. That file is the list of settings and documents each one.

    Config files are flat YAML, one key per setting. Paths may start with ~ and relative paths are taken from the current directory. Flags are on for 1, true, yes or on (any case) and off for any other value, so RUNSHEETS_OPEN=off switches off an open: true in the file, and --no-open switches off either. A blank value (RUNSHEETS_PORT=) counts as unset. A port that is not a whole number from 1 to 65535, a log level that is not one of the five (in any case: WARN is warn), a named config file that does not exist, a config file that is not valid YAML, a --bind host that does not resolve, or a runbook directory that cannot be read is reported in one line and the command exits 1:

    runsheets: port must be between 1 and 65535, got 70000

    # ~/.config/runsheets/runsheets.yml
dir: ~/ops/runbooks/db-refresh
port: 4580
runs_dir: ~/ops/runs
open: true

    With that file, plain runsheets serves the db-refresh runbook on port 4580 and opens the browser; runsheets --check checks it instead; and RUNSHEETS_PORT=4581 runsheets or runsheets -p 4581 moves it for one run. A repository can carry its own config/runsheets.yml (say dir: and runs_dir:) that applies whenever runsheets is run from its root. One thing it cannot do is open the server to the network: a non-loopback bind: set only by that file stops the start with runsheets: ./config/runsheets.yml sets bind: 0.0.0.0, which is not a loopback address…. Pass --bind or set RUNSHEETS_BIND if that is really wanted.

    Variable Effect
    RUNSHEETS_CONFIG The file read in place of ./config/runsheets.yml, when --config is not given.
    RUNSHEETS_<SETTING> The setting of that name, as above.
    RACK_ENV Selects an environment section (development, test, production) in defaults.yml; none is required.
    PORT Not used. Set RUNSHEETS_PORT or pass --port.
    anything else Inherited by every executed block, and used to pre-fill inputs of the same name. See Inputs and Secrets.

    Saving settings¶

    --dump prints the settings in force, after every layer has been applied, in the shape of a config file, and exits. Redirect it to save them. Run it with the options you want to keep and they become the defaults for later runs:

    runsheets --dump -p 4580 ~/ops/runbooks/db-refresh        # look first
runsheets --dump -p 4580 ~/ops/runbooks/db-refresh > ~/.config/runsheets/runsheets.yml
runsheets                                                  # now serves db-refresh on 4580

    Redirect to config/runsheets.yml instead for a project config to commit with a repository. dump itself is never in the output, so a saved file cannot make every later run print and exit, and neither is check, for the same reason. Nor is why: the reason for a session belongs to that session, not to every later one. engineer is saved.

    About --bind¶

    The default binds to loopback and the server only accepts requests whose Host header is localhost, 127.0.0.1, ::1 or the bind address. That is the whole multi-user story: there is none. Binding to another address exposes shell execution on your machine to whoever can reach that address, protected only by the session token embedded in the pages. Do not do it on a network you do not control. The command prints a warning whenever the bind address is not loopback. A wildcard address (0.0.0.0 or ::) answers on every interface, so the Host check is turned off for it; a specific address accepts requests for itself and the loopback names.

    The session¶

    Everything from start to stop is one session, belonging to one engineer and opened with a note saying why (see Sessions, Runs and Runsheets). The engineer and the reason come from --engineer and --why, RUNSHEETS_ENGINEER and RUNSHEETS_WHY, or engineer: and why: in a config file. With both set, the session starts as the server does. Otherwise the browser opens on a start page that asks for them, with the name pre-filled from the configured engineer, else git config user.name, else $USER. The name is taken as given; nothing authenticates it.

    At start, any earlier session in the same runs directory that is still marked running but whose process is gone is closed as interrupted, along with its runs.

    The session log¶

    Every session writes session.log in its directory under <runs-dir>/sessions/ (see The Run Record). log_level sets what goes into it:

    Level What is logged
    debug Everything in the rows below, plus page views and other requests, searches, polling, runbook reloads, and the environment handed to each execution, secrets shown as [secret].
    info Every action and its output: the session starting and ending, notes, a run opened with its inputs, inputs changed, each execution with its code and output, exit 0, stop requested, stopped, step marks and terminal confirmations with their notes. The default.
    warn Non-zero exits, timeouts, refused actions (a destructive block without its code or with the wrong one, any other action refused with 409), authoring warnings when a run opens, and an earlier session found interrupted.
    error An execution that cannot start, a runbook that no longer loads, an exception in the server.

    fatal is accepted too; runsheets writes nothing at that level, so it leaves the file empty.

    The log is echoed to the terminal that started runsheets, at info whatever the file's level, unless --quiet, RUNSHEETS_QUIET or quiet: true turns the echo off. Secret values never reach the log.

    Stopping¶

    Ctrl-C ends the session and stops the server, exactly like End session on the session page. Every run is closed with a status worked out from what was done (completed, partial or opened), anything still running in any runbook (a background block, a block that was still going) is stopped, and the records are written, so nothing outlives the tool and no record is left saying running. If the process is killed instead, the next start closes its session as interrupted.
